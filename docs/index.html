How Syntropy Health works

Technical overview for users, reviewers and EHR app-program teams.

1. Application summary

Syntropy Health is a patient-facing, self-hosted personal health record (PHR). An individual runs it on their own computer or home server (Docker or Python). Using the SMART App Launch standalone patient launch, it retrieves that individual's own records from their healthcare organizations and stores them in a local SQLite database, where they can view trends, prepare visit summaries and export their data. There is no Syntropy-operated backend that receives patient data.

Intended usersPatients and caregivers (parents, adult children managing a parent's records with proxy access).
Launch typeStandalone patient launch, public client, authorization code + PKCE (S256). offline_access requested for scheduled refresh.
FHIR versionR4 (US Core / USCDI).
AccessRead-only (patient/*.read or per-resource read scopes).
Redirect URIhttps://health.syntropylabs.io/callback

3. The callback relay

OAuth requires a fixed HTTPS redirect URI, but every Syntropy instance has its own private address. The relay page bridges that gap:

  • It is a static file with a strict Content-Security-Policy. It loads no scripts, fonts or images from anywhere and makes no network requests.
  • It reads the destination from the state parameter and accepts only loopback, private-network, Tailscale and .local hosts, so it cannot redirect to the public internet.
  • The only secret-bearing value it handles is the one-time authorization code, which cannot be redeemed without the PKCE verifier held by the instance.

Oura and WHOOP don't support PKCE-only public clients and require a client secret. For those two, an edge worker at syntropy-auth-relay.syntropylabs.workers.dev performs the code exchange, then hands the tokens to your instance in the URL fragment (never sent to any server) and keeps no copy. Renewals go through the same worker. Users who register their own developer apps can keep the whole exchange local.

5. Security

  • Dashboard protected by a passphrase (scrypt); sessions are opaque, hashed server-side, HttpOnly, SameSite.
  • OAuth tokens and secrets encrypted at rest; a per-instance key never leaves the machine.
  • Phones sign in with the passphrase or a single-use code and receive individually revocable device tokens; the passphrase is never stored on the phone.
  • Every sign-in, sync and export is written to a local activity log the user can review.
